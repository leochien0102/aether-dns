## 2. 各 Job 有效权限与写权限用途审计

`release.yml` 顶层声明了 `permissions: { contents: read }`。根据 GitHub Actions 权限继承规则，未声明 job 级 `permissions` 的 job 继承顶层权限；显式声明 job 级 `permissions` 的 job 仅拥有所声明范围（其余权限默认为 `none`）。本次审计仅记录现状，未修改任何权限声明，也未提权。

| Job | 触发 / 依赖条件 | 显式 `permissions` | 有效权限 | 写权限用途 |
| --- | --- | --- | --- | --- |
| `binaries` | 无 `needs` | 未声明（继承顶层） | `contents: read` | 无写权限。仅检出源码、构建 `x86_64` / `aarch64_generic` 静态 musl 二进制并上传 `binary-*` workflow artifact。 |
| `packages` | `needs: binaries` | 未声明（继承顶层） | `contents: read` | 无写权限。仅检出源码、下载 `binary-*` artifact、调用 OpenWrt SDK 打包 `.ipk`/`.apk` 并上传 `package-*` workflow artifact。 |
| `verify` | `needs: packages` | 未声明（继承顶层） | `contents: read` | 无写权限。仅检出源码、下载 `package-*` 与 `binary-*` artifact、生成 `SHA256SUMS` 并校验载荷/元数据、打包并上传 `release-assets` 内部传输 artifact。 |
| `release` | `needs: verify` 且 `if: startsWith(github.ref, 'refs/tags/v')` | `contents: write` | `contents: write` | 通过 `GH_TOKEN: ${{ github.token }}` 执行发布步骤：<br>1. `gh api "repos/$GH_REPO/releases/tags/$TAG"`：只读查询目标 tag 是否已存在 Release，防止重传（仅明确 `HTTP 404` 时继续）；<br>2. `gh release create "$TAG" --verify-tag --notes-file release-notes.md`：创建目标 tag 对应的 GitHub Release（需 `contents: write`）；<br>3. `gh release upload "$TAG" "$asset"`：按固定顺序上传 7 个发布资产（2 个 `.ipk`、2 个 `.apk`、2 个裸二进制、`SHA256SUMS`）至该 Release（需 `contents: write`）。 |
