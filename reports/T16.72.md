## 1. 根因与修复

1. **合法答案最低 TTL = 0 的缓存与刷新语义（`src/cache.rs`）**
   - 基线 `Cache::add` 未拦截 `ttl == 0`，导致当 `cache_stale > 0` 时，TTL=0 的合法答复被写入缓存并在 stale 窗口内继续被提供；后台刷新收到合法 TTL=0 答复时也会覆盖为可继续服务的 stale 条目。
   - 修复：在 `Cache::add` 通过全部合法性校验并由 `ttl_fields`（已忽略 type 41 OPT 伪 TTL、仅取 answer 段非 OPT RR 最小 TTL）求得 `ttl == 0` 时，调用 `self.remove(key)` 清除同键旧缓存并返回 `false`。
   - 调用方效果：
     - 首次未命中查询：`server::forward` 仍向客户端返回本次合法 TTL=0 响应，但不会缓存。
     - 已有同键缓存的刷新：`finish_refresh` 调用 `self.add` 清除旧条目后，`self.entries.get_mut(key)` 为 `None`，后续查询不会继续提供旧缓存，直接回源。
     - 刷新超时（`response = None`）或无效/被拒报文（损坏报文、TC、SERVFAIL、空 answer、无 A/AAAA）：在 `ttl == 0` 判断前返回 `false`，不删除旧条目，保留原有 5 秒退避重试语义。

2. **极端 stale 窗口与 `retry_after` 溢出边界（`src/cache.rs`）**
   - 基线 `Cache::begin_refresh` 使用 `ttl + Duration::from_secs(self.stale)`，当合法配置的 `cache-stale` 接近 `u64::MAX` 时会触发 `Duration` 加法 panic；同时 `Cache::get` 使用 `u64::from(entry.ttl).saturating_add(self.stale)`，与精确数学过期边界及 `begin_refresh` 不一致。
   - 基线 `Cache::finish_refresh` 使用 `now + Duration::from_secs(5)`，当模拟时钟接近 `Duration::MAX` 时会触发 `Duration` 加法 panic。
   - 修复：
     - 抽取共享方法 `Cache::lifetime(&self, entry, now) -> Lifetime` 供 `get` 与 `begin_refresh` 共用。在 `elapsed >= ttl` 时通过 `elapsed - ttl < Duration::from_secs(self.stale)` 判断 stale 窗口，全程无溢出且在 `[Duration::ZERO, Duration::MAX]` 区间内与精确过期边界完全一致。
     - 将 `Entry.retry_after: Duration` 替换为 `Entry.last_failure: Option<Duration>`，退避判断改为 `now.saturating_sub(at) < Duration::from_secs(5)`，避免 `Duration::MAX` 附近溢出并保持精确 5 秒冷却窗口。
