## 实现和失败行为

`use_china_reply` 改为异步，两个 `none_exchange` 调用点都等待真实 membership 结果。IPv4 的 `IpTest::is_china` 整体（包括生产实现的 mutex 等待和 Netlink contains）进入 `tokio::task::spawn_blocking`，而不只是把调用外围包装成 async。

使用一个进程级静态 Tokio semaphore，固定 **8** 个额度。生产后端本身通过 mutex 串行访问，8 个额度提供少量并发余量，同时限制等待 mutex 或阻塞池排队的工作；不是线程数、超时或吞吐承诺，也不新增配置和依赖。

- 投递前 `try_acquire`，满额不等待、不创建额外阻塞工作。
- permit 移入阻塞闭包，直到真实 `is_china` 返回或 unwind 才释放。取消 async 调用方、丢弃 JoinHandle 或关停 DNS 服务均不提前归还额度。尚在阻塞池排队的工作也占额度。
- 满额、JoinError（例如阻塞任务 panic / 运行时取消尚未执行的任务）都返回当次“不选 china”，**不写 verdict**，没有新增逐次错误日志。
- 沿用原来的双侧结果合并：有 trust 响应时优先 trust；trust 失败但 china 有合法响应时仍可退回 china；双方交换失败时保留原错误规则。这里不把本地饱和伪装成已确认的非成员。
- 真正的 IPv4 true/false 仍缓存；`IpTest` 的既有 bool 契约不变，真实内核错误仍由原实现记录并作为 false。IPv6 不调用 `IpTest`，仍按 false 记录；TC、无 IP、DNS 错误等原分支保持不变。
- 没有 verdict/cache 锁跨 await；仅取得真实判定后短暂锁定 verdict。
- 未修改 answer cache 契约、配置、上游 ID、Netlink 超时以及集合写入路径。`ip_writer::write_reply` 仍在原位置、发送回包之前执行；本卡不卸载写入。

## 因果验收：不是用耗时猜测 reactor 是否阻塞

专项 `server::offload::blocked_membership_keeps_reactor_live_and_quota_until_real_completion` 使用手工构建的 **current_thread** runtime、内存注入的同步 `IpTest`、`Mutex + Condvar` 屏障及 `Notify` 入口信号，真实 DNS 客户端/上游均为回环 UDP。

1. 向真实 DNS listener 发送 A 请求，收到 `is_china` 已进入的信号。该同步方法停在关闭的 Condvar 屏障上，不能自行返回。
2. 通过同一 DNS listener 发送不依赖 IPv4 membership 的 AAAA 请求，收到 trust 正常应答；此时断言屏障仍关闭且 membership 调用数仍为 1。证明发生在解除屏障**之前**，不靠 sleep、吞吐阈值或线程池容量推断事件循环存活。
3. 逐个手工 poll 另外 7 个真实 `use_china_reply` future 至 Pending，确认投递后总可用额度为 0。专项将阻塞池限制为 1 个 worker，故屏障内的 1 个调用之外，另 7 个已投递工作确定仍在排队；池大小只用于构造排队，不是步骤 2 的非阻塞证据。
4. 满额再查询：立即返回不选 china，verdict 为 None，实际 `IpTest` 调用数不增加。
5. 丢弃 7 个排队任务的等待 future，再关停持有执行中查询的服务。`serving.await` 在屏障关闭时返回，全部 8 个额度仍被持有，重试仍遭拒。覆盖排队取消、执行中取消和服务关闭不在事件循环内同步 join 阻塞线程。
6. 未解除屏障时启动另一个服务实例，真实同名 A 请求按当次退让选择 trust，额度仍为 0、实际调用数仍为 1，验证进程共享限额且没有继续投递。
7. 解除屏障，在单 worker FIFO 后投递一个完成标记，等待既有工作全部完成。确认实际调用数恰为 8（饱和期间无额外排队），额度全部恢复。
8. 向第二个服务再次发送步骤 6 的同名 A 请求：现在正常选 china，membership 调用增加一次；再次查询命中真实 china verdict，不再调用 membership。证明满额没有留下 false verdict，取消后的队列也能排空恢复。
9. 注入阻塞任务 panic，确认 JoinError 的当次退让不缓存，permit 也正常释放。`--nocapture` 中对应 panic 文本为预期注入，测试本身通过。

独立 OS 线程看门狗使用 `std::sync::mpsc::recv_timeout(20s)`；若夹具失控先释放屏障再 abort 测试进程，避免 reactor 被同步阻塞时连 Tokio timeout 都无法运行。20 秒仅为夹具救援上限，不作为通过标准。

为避免新增生产测试 API，专项在自己的 integration target 内 include 原 `server.rs` 并测试私有入口；其余回归测试仍通过已有服务端注入入口执行。

## 边界与残留风险

- 本次阻塞由注入的同步屏障模拟；没有在真实 nft 表/真实内核 Netlink 阻塞上做设备实验，不能据此宣称真实 syscall 已被中断或其耗时有新的上限。
- 保留原 Netlink 超时；`spawn_blocking` 不能强杀已经进行的 syscall。若内核调用不返回，对应额度持续占用，满额后新 membership 仅按上述规则退让。
- 服务端异步关停仍使用原有共享 500 ms drain 窗口，未同步 join 阻塞工作。Tokio runtime 自身销毁仍可能等待未完成的阻塞任务；这发生于退出 async 事件循环之后，不承诺进程硬限时退出。专项先解除屏障、确认工作完成，再销毁 runtime。
- 集合写入仍同步且顺序完全不变，这是 H11 后续任务范围；本卡只解决 membership 读取对事件循环的阻塞。
