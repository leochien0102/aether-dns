## 关键设计取舍

1. `get()` 与 `begin_refresh()` 在同一个短生命周期 cache mutex 临界区内执行；只有已命中的请求能登记刷新。fresh 以原始最小答案 TTL 判断，精确比较 Duration 的 `remaining <= ttl/3`，且原始 TTL 至少 10 秒。stale 窗口内不限此最小 TTL，客户端继续立即取得所有 RR TTL0。
2. 独立的在途 key 集合最多 4 项，不排队、不全量扫描。集合不随条目淘汰而删除，因此条目淘汰/重插时仍不会同时启动相同 key 的第二个刷新。名额在刷新完成后释放；满额的命中照常返回缓存，后续命中重试登记。
3. 刷新与未命中均调用 `exchange_response()`，使用同一 route、上游组、`none_exchange()`、传输选择、RA/additional 归一化；不递归查询缓存。后台任务不触发客户端错误路径，也不额外执行命中 writer。
4. 刷新成功只调用现有 `add()`；TC、空地址答案、非 0|3 等原有拒收响应不覆盖旧条目。传输错误/归一化错误/拒收均视为刷新失败，旧条目保留，完成时起 5 秒内不再刷新该条目；不延长旧条目的原有新鲜/stale 有效期。
5. 冷却只占已有条目的一个时间字段；失效/淘汰会正常释放旧条目，不引入无界失败 key 表。缓存容量为 0 无条目、无刷新；stale 为 0 仍允许 refresh-ahead，但到 TTL 必然 miss。
6. 后台 `JoinSet` 置于 `Mutex<Option<_>>`，派生时回收完成任务；shutdown 取走并丢弃 JoinSet，取消所有刷新，`None` 阻止正在 drain 的客户端请求再次派生。后台刷新不参与原有 500 ms 客户端 drain 预算。所有 `std::sync::Mutex` guard 均不跨 await。
7. 旧的网络 TTL 测试在临近过期命中后可能与新刷新竞争，故将只验证 TTL 递减的网络采样移到阈值前，将精确 9999 ms TTL1、10000/14999 ms TTL0 的条目断言放到 FakeClock 单元测试；真实后台刷新行为由受控上游集成测试验证，不以调度顺序猜测上游次数。

### 单元验收映射

- `refresh_threshold_and_inflight_deduplication`：TTL12，7999 ms 不触发；8000 ms 等号边界触发，第二次不触发。
- `short_ttl_only_refreshes_when_stale`：TTL9，8999 ms 不触发；9000 ms stale 命中 TTL0 且触发。
- `failed_refresh_retains_entry_and_cools_down_for_five_seconds`：失败保留 TTL0；4999 ms 不重试，5000 ms 可重试。
- `expired_entries_miss_and_stale_zero_still_allows_refresh_ahead`：stale=0/5 均允许 refresh-ahead；到 TTL+stale 时 miss 且不能登记刷新。既有 `exact_stale_end_is_miss_and_reinsert` 还验证越过窗口后的 miss。
- `refresh_limit_is_four_and_released_after_failure`：四个不同 key 占满后第五个不刷新；失败释放名额。
- `rejected_refresh_replies_never_overwrite_old_entry`：TC、空答案、SERVFAIL 刷新均保留原应答且进入冷却。
- 既有 TTL 递减、ID/归一化、TTL0、容量/LRU、禁用缓存、UDP/TCP 共享缓存、过滤优先级等全部通过。

### 集成验收映射

- `refresh_ahead_returns_old_ttl_before_gated_upstream_and_updates_cache`：首查计数 1，紧接命中计数仍 1；阈值前不刷新；阈值处客户端先拿 TTL4，上游响应仍被闸门阻塞；观察上游计数变为 2 后释放 TTL30 响应，再查 TTL30。
- `ten_concurrent_stale_hits_refresh_once_and_shutdown_cancels_refresh`：10 个并发查询均先返回 TTL0；上游总计 2（首查+一次刷新），无重复请求；保持刷新上游不应答时 shutdown 在 750 ms 测试预算内完成。
- `failed_refresh_preserves_client_response_and_cools_down`：上游刷新返回 SERVFAIL，客户端始终收到与刷新前逐字节相同的 NOERROR/TTL0 应答；冷却末前不增加上游计数，5 秒边界可再次刷新并成功回写。
- `at_most_four_distinct_keys_refresh_concurrently`：5 个 key 均返回旧条目，但只启动 4 个刷新；释放一个后，第五个 key 的后续命中才启动刷新。
