## M4-10 发布流水线：tag 触发产出四资产与校验清单（**冻结 2026-11-11**）

- **单一目标**：在本仓库建立 tag 触发的 CI，交叉编译静态 musl 二进制、按四矩阵打包、产出与发布要求逐字一致的四个资产和 `SHA256SUMS`。
- **分支**：`feat/m4.10-release-pipeline`
- **卡片版本**：以本卡冻结提交为准（见发卡入口提示）；本卡不记录自身提交号

> 前置：[M4-03](m4-03.md)（版本 `1.0.0`）、[M4-09](m4-09.md)（`openwrt/Makefile`）均已合并。
> 所有者 2026-11-11 授权：仓库已建（`leochien0102/aether-dns`，当前 **private**），`main` 已推送，旧设计历史保留在分支 `design-20261102`。
> **tag 与 Release 由设计负责人执行**；实现者只交付 workflow 与本地可验证的证据，不推 tag、不发布、不改仓库可见性。

## 背景与证据

- 矩阵与工具链在 aether-proxy 侧已跑通：`aether-proxy/.github/workflows/build.yml` 使用 `openwrt/gh-action-sdk@v11`，SDK `24.10.8`（ipk）与 `25.12.5`（apk），ARCH `x86_64-*` 与 `armsr-armv8-*`，package_arch `x86_64` 与 `aarch64_generic`。
- 本仓库 `openwrt/Makefile` 只打包预置二进制（M4-09），产物实测 `aether-dns_1.0.0-r1_aarch64_generic.ipk`，control `Version: 1.0.0-r1`、`Provides: dns-engine`、无 `Depends` 行、无 `Default-Variant`（ipk 预期）。
- apk 侧：`Default-Variant` 会转成 `provider-priority:100`（SDK `include/package-pack.mk:358`），资产名由 channel 规则规范成 `{name}-{version}_{arch}.apk`（`aether-proxy/tools/channel/build.py:139`）。
- 本机无法交叉编译（`rustlib` 只有 `x86_64-unknown-linux-gnu`、无 rustup、无 docker），故静态产物只能在 CI 产出。

## 允许改动

- 新增 `.github/workflows/release.yml`（唯一工作流文件）
- 新增 `tests/ci/verify-assets.sh`（资产名/校验和/元数据断言的脚本，供 workflow 调用）
- `openwrt/Makefile`（**仅**两处：显式固定 `PKG_SOURCE` 以去掉绝对路径；补 `PKG_LICENSE_FILES:=LICENSE`）
- `openwrt/README.md`（补 CI 用法）
- `docs/tasks/m4.md`（索引）
- `reports/M4-10.md`

不改 `src/`、`tests/`（除新增 `tests/ci/`）、`Cargo.toml`/`Cargo.lock`、`docs/design`、其他仓库与 channel。

## 做什么

### 1. 交叉编译（job `binaries`）

1. `x86_64`：`rustup target add x86_64-unknown-linux-musl`，用 `musl-gcc` 作为 linker。
2. `aarch64`：`rustup target add aarch64-unknown-linux-musl`，用 aarch64 musl 工具链作为 linker（可用 `taiki-e/setup-cross-toolchain-action` 或等价固定版本 action；**版本必须钉死**）。
3. 构建参数：`cargo build --release --locked --target <triple>`，`RUSTFLAGS="-C target-feature=+crt-static"`（musl target 默认静态）。
4. 断言：`file` 显示 `statically linked`；`readelf -d` 无 `NEEDED`；`./aether-dns -V` 输出 `aether-dns 1.0.0`（aarch64 用 `qemu-aarch64-static`，经 `docker/setup-qemu-action` 注册 binfmt）。
5. 上传两个二进制为 artifact。

### 2. 四矩阵打包（job `packages`）

矩阵（与 proxy 同构）：

| SDK | ARCH | package_arch | 扩展名 |
|---|---|---|---|
| 24.10.8 | `x86_64-24.10.8` | `x86_64` | ipk |
| 24.10.8 | `armsr-armv8-24.10.8` | `aarch64_generic` | ipk |
| 25.12.5 | `x86_64-25.12.5` | `x86_64` | apk |
| 25.12.5 | `armsr-armv8-25.12.5` | `aarch64_generic` | apk |

每个组合：放入对应二进制到 `openwrt/files/aether-dns` → `openwrt/gh-action-sdk@v11` 构建 `aether-dns` → 从 `bin/packages/<arch>/<feed>/` 取产物。

### 3. 资产归一化与断言

1. 规范化成四个名字（**逐字一致**）：
   `aether-dns_1.0.0-r1_aarch64_generic.ipk`、`aether-dns_1.0.0-r1_x86_64.ipk`、
   `aether-dns-1.0.0-r1_aarch64_generic.apk`、`aether-dns-1.0.0-r1_x86_64.apk`。
2. `tests/ci/verify-assets.sh` 断言：
   - 文件名集合与上表完全相等（多一个少一个都失败）；
   - ipk：`tar -xzOf <ipk> ./control.tar.gz | tar -xzO ./control` 里 `Version: 1.0.0-r1`、`Provides: dns-engine`、`Architecture` 与矩阵一致、无 `Depends: libc`、`Source:` **不含绝对路径**；
   - apk：`.PKGINFO` 含 `provides = dns-engine` 与 `provider-priority = 100`，版本 `1.0.0-r1`；
   - `SHA256SUMS` 覆盖四个资产且 `sha256sum -c` 通过。

### 4. 发布（job `release`）

1. 触发：**两路**——`on: push: tags: ['v*']`（正式发布）与 `on: workflow_dispatch:`（合并前的实证运行）。
   workflow_dispatch 只允许在分支上跑，用来产出四资产与校验结果，**不得创建 Release**。
2. release 作业必须加守卫 `if: startsWith(github.ref, 'refs/tags/v')`；非 tag 引用只上传 workflow artifact 供人工核对。
3. **发布时不重传**：若该 tag 的 Release 或其任一资产已存在，作业失败退出，不覆盖、不删除。
4. 创建 annotated tag 的对象是设计负责人推的 tag；workflow 只做 `gh release create <tag> --verify-tag --notes-file ...` 与上传。
5. 资产上传顺序固定；`SHA256SUMS` 最后上传。

## 不做什么

- 不推 tag、不创建 Release、不改仓库可见性、不碰 `aether-proxy*` 与 channel 仓库。
- 不把 Rust 编译放进 SDK；不引入非钉死版本的构建 action。
- 不改包版本、不改 `-V` 输出、不改查询行为。
- 不实现 sign/签名（channel 侧负责）。

## 停点

- CI 需要超出 `GITHUB_TOKEN` 的凭据（例如跨仓库触发）→ 停下汇报。
- 仓库 Actions 未启用或不可用 → 停下汇报。
- 任何一个矩阵组合无法产出预期资产名 → 停下，不带病发布。
- 需要新增非钉死 action 或修改 SDK 版本 → 停下汇报。
- 发现 tag 已存在同名 Release → 停下（不能覆盖）。

## 交接分工（2026-11-11 冻结）

实现者**不推任何远端**。CI 证据按两段产生：

1. 实现者完成代码、本地能跑的门禁（`cargo fmt/clippy/test`、`tests/review.sh`、脚本静态检查），提交到本卡分支并交回；
2. **设计负责人**推送该分支、执行 `gh workflow run release.yml --ref <分支>`，把运行链接与四资产/校验结果回给实现者（或直接写进复审记录）；
3. 实现者据运行结果补完报告与最终提交，再由设计负责人复审合并。

报告必须区分「本地已验证」与「CI 已验证」，并附 CI 运行链接；**没有运行链接不得声称 CI 通过**。

## 验收（可判定）

1. 在 PR/分支上手动 `workflow_dispatch` 跑一次：四个资产 + `SHA256SUMS` 全部产出，`tests/ci/verify-assets.sh` 通过，日志贴出四份 control/`.PKGINFO` 关键字段与 `sha256sum -c` 结果。
2. 四个二进制 `-V` 均为 `aether-dns 1.0.0`（aarch64 经 qemu）。
3. `file`/`readelf -d` 证明静态、无 `NEEDED`。
4. 重传保护可验证：对同一 tag 再跑一次，作业必须失败且不覆盖既有资产（用 dry-run 或本地模拟，不做真实发布）。
5. `bash tests/review.sh` FAIL=0；`git diff --stat main...HEAD` 只含允许改动。
6. 报告写明"未推 tag、未发布"，并附 design owner 后续推 tag 的步骤。
