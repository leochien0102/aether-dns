### M4-01 缓存刷新（**复审、合并及真机指标验收通过，2026-11-07**）

- **单一目标**：缓存命中时按 TTL 阈值异步刷新条目，使持续有流量的名字不再长期以 TTL=0 应答。
- **分支**：`m4/cache-refresh`
- **背景/证据**：`M3-REPORT.md` §6：146 样本 TTL0 占 88.4%；65 分钟周期
  = 300 s 新鲜 + 3600 s stale；`src/cache.rs` 的 `get()` 过期后一律回 TTL0，没有任何刷新。
- **允许改动**：`src/cache.rs`、`src/server.rs`、`tests/cache.rs`、新增 `tests/cache_refresh.rs`。
  **不改** `src/config.rs`、不改 aether-proxy、不新增配置指令、不做负缓存。
- **语义（冻结）**：

  1. 仅命中路径触发。新增 refresh-ahead：条目 fresh 且
     `remaining <= ttl/3` 且 `ttl >= 10 s` 时后台刷新一次；
     客户端立即拿到当前响应，TTL 照常递减。
  2. stale 命中（`elapsed >= ttl` 且 `< ttl + cache-stale`）：立即返回 TTL0（现状不变），
     同时后台刷新。
  3. 刷新与客户端未命中走同一套 route/exchange；**并发上限 4**；同一 cache key 在途去重。
  4. 失败：保留旧条目、不向客户端报错；同一 key **5 s 冷却**内不重复刷新。
  5. 成功回写只走既有 `add()` 校验；TC / 空答案 / 非 `0|3` 不覆盖旧条目。
  6. `cache` 为 0 不刷新；`cache-stale` 为 0 时只有 refresh-ahead，没有 stale 命中。
  7. shutdown 时后台刷新任务不得阻塞退出。

- **不做**：定时全量扫描；改 TTL0 语义；负缓存；TTL min/max；cache-db。
- **验收**：

  1. `cargo fmt --all -- --check`、`cargo clippy --all-targets -- -D warnings`、
     `cargo test --all` 全过；`bash tests/review.sh` FAIL=0。
  2. 单元（`tests/cache.rs`，FakeClock）：`remaining > ttl/3` 不触发；`<= ttl/3` 触发一次；
     `ttl < 10 s` 不触发；stale 触发；冷却期内不重复；超过 `ttl + cache-stale` 仍 miss。
  3. 集成（`tests/cache_refresh.rs`，fake upstream 计数）：首查上游 1 次；紧跟再查 0 次；
     推进到阈值后查询**立即返回旧 TTL**，随后上游 +1，再查 TTL 已更新；
     10 个并发 stale 查询只产生 1 次刷新；刷新失败不改客户端应答。
  4. 既有 `tests/cache.rs` 的 TTL 递减、TTL0、容量淘汰不回归。

- **停点**：需要改配置/渲染/新增指令，或无法在 `std::sync::Mutex` 不跨 await 的前提下实现时，
  停下汇报，不自行扩大范围。
- **真机验收**（设计负责人另做）：10 s 间隔查询 10 分钟，TTL0 占比 <5%，无 SERVFAIL，
  上游 QPS 有界。

### M4-04 重启期间 DNS handoff 不得泄漏到直连（P0，T15.1 已验收合并）

实现卡：aether-proxy [`T15.1`](../../../aether-proxy/docs/tasks/m15.md)，分支 `fix/t15.1-restart-dns-handoff`。
本仓库保留跨项目验收输入，不在 aether-dns 内实现。

来源：2026-11-06 21:12 授权受控 restart 实测（不是推断）。证据与数据在
`dist/logs/h28k-weekend/startup-gap-analysis.md`、`probe-restart-2026-11-06T2112.csv`
（本地证据，不入库）。

实测：

- 21:12:01.5–07.7 客户端对随机 `x*.google.com` 得到 **NXDOMAIN、约 300 ms**；
- 同一窗口 31053 无监听、Xray 未启动，随机域名不可能命中缓存，
  因此这些应答只能来自直连解析器；
- 机制：`/tmp/dnsmasq.d/aether-proxy.conf` 内容为 `no-resolv` +
  `server=127.0.0.1#31053`；`daemon.uc` 停止路径调用 `apply.dnsmasq_remove`，
  删除 fragment 并重启 dnsmasq；fragment 消失后 dnsmasq 回落到
  `resolv-file=/tmp/resolv.conf.d/resolv.conf.auto`（223.5.5.5）。

影响：每次 restart/升级约有 6 s LAN DNS 绕过代理；被墙域名可能拿到直连结果，
且不产生任何 aether-dns 日志（这段没有监听者）。

目标：restart 不得出现直连解析窗口；用户主动 stop 仍按现行为释放 handoff。

边界：只改 aether-proxy 启停编排；不改 aether-dns 查询语义；不改变 stop 的既有语义。

验收：

1. 同法受控 restart（随机 gfw 域名 10 qps）：无“NXDOMAIN 且约 300 ms”的直连窗口；
2. 设备侧 100 ms 采样 `/tmp/dnsmasq.d/aether-proxy.conf`：restart 全程存在；
3. 主动 stop：fragment 仍被移除、DNS 恢复直连（现有语义不回退）；
4. 恢复后 T1、PROXY_HEALTHY。

已冻结决策（2026-11-07）：

1. 用 `/var/run/aether-proxy/` 内易失的 restart intent 区分 restart 与普通 stop；新 handoff 成功安装后才清除；
2. restart 期间采用 fail closed：允许 timeout/SERVFAIL，不允许回落直连；
3. 手动 stop、`enabled=0`、无 intent 的 cleanup 仍删除 handoff 并恢复系统 DNS；
4. 本卡不处理 Xray DNS inbound 就绪窗口，也不宣称零中断。

### M4-05 启动期 SERVFAIL 窗口（P1）

aether-proxy T15.4显式节点查询器（B1）及T15.5引用驱动readiness（B2）已合并（`a417edf`/`e80b2e2`）；当前冻结T15.6隔离bootstrap生命周期与启动编排（B3，`docs/tasks/m15.md`）。B3及后续真机窗口验收完成前，不宣称启动SERVFAIL缺口已修复。

实测（同日两次 restart）：

- 21:12:11.8–13.6：child 已监听 31053、Xray 未监听 31082/31083，
  客户端 58 条 SERVFAIL；设备日志 21:12:11–13 多条 refused；
- 17:21 同类事件 6 条 refused（当时被误读为“只有 6 个查询受影响”）。

（`daemon.uc`），DNS 先于 Xray 的 DNS inbound 可用。

目标：T1 启动期间不再出现“有监听、无上游”的窗口。

边界：只调启动顺序/就绪判定；不改运行期路由与列表语义；节点域名仍走直连兜底。

验收：

2. 无 LKG 的冷启动同样满足；
3. 节点域名解析不依赖 Xray；
4. 运行期 T1/T2/T3 与模式行为不回归。

待决策：bootstrap 解析路径（LKG 优先 / 直连解析器）、是否同时等 31082 与 31083。

停点：若需改 Xray 渲染或新增 bootstrap 解析器，先停下确认范围。

### M4-07 测试端口竞争修复（**复审通过并合并，2026-11-07**）

- **单一目标**：消除测试 harness 的端口竞争假失败，使全量测试可重复通过。
- **分支**：`m4/test-port-race`
- **证据（2026-11-06 M4-01 复审）**：
  - `cargo test --all` 在 `tests/tcp_forward.rs` 失败：`Address already in use (os error 98)`；
    该文件不在 M4-01 的 diff 里；
  - 同一 harness 单独跑 `cargo test --test tcp_forward` 5/5 通过；
    `bash tests/review.sh` 时而 `FAIL=0`、时而失败；
  - 机制：harness 先 `bind("127.0.0.1:0")` 预留端口，随即 `drop`，再 spawn 子进程绑定；
    窗口内其他并行测试可能抢占该端口。
  - 涉及：`tests/tcp_forward.rs:32`、`tests/udp_forward.rs:32`、
    `tests/tcp_timeout.rs:42`、`tests/tc_clear.rs:90`。
- **允许改动**：`tests/` 下的 harness（可新增 `tests/common/` 或等价共享模块）；
  **不改** `src/`、`tests/review.sh`、`Cargo.toml`。
- **要求**：

  1. 启动失败判定：子进程在预期 listening 行之前退出，或 stderr 出现绑定错误
     （含 `Address already in use`），即视为本端口失败。
  2. 有界重试：换新端口重试，最多 10 次；每次失败必须 kill + wait 子进程、
     删除临时 conf，不泄漏进程或文件。
  3. 成功路径行为不变：断言、超时、查询语义不放松；不得用 sleep 掩盖竞争。
  4. 同一模式的多处 harness 优先抽公共 helper，至少覆盖上述 4 个文件。

- **验收**：

  1. `cargo test --all` 连续 10 次全过；
  2. 两个并发进程分别跑 `cargo test --test tcp_forward` 与
     `cargo test --test udp_forward`，连续 3 轮全过（复现原竞争条件）；
  3. `bash tests/review.sh` 连续 3 次 `FAIL=0`；
  4. `git diff --stat main...HEAD` 只含 `tests/` 与报告；
  5. `cargo fmt`、`cargo clippy` 通过。

- **不做**：改被测二进制、改 `review.sh`、放宽或删除既有测试、引入新依赖。

- **停点**：需要改 `src/`、`review.sh`、`Cargo.toml`，或无法在不加 sleep 的前提下稳定时，
  停下汇报。
- **依赖说明**：与 M4-01 独立；建议先合并 M4-07，再合并 M4-01（或 M4-01 分支
  merge main 后重跑门禁）。
