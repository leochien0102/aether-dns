# 04 决策状态与交叉审查入口

## 1. 已明确的方向

- 独立项目 aether-dns，优先 Rust。
- 现有基本功能稳定优先，多出口分流不急，不与 DNS 重写同步上线。
- 目标是可长期维护与扩展，不是为了替换组件而替换。
- 本轮只准备方案，未授权开始完整实现或切换实际服务。

## 2. 本稿的建议（尚未批准）

| 编号 | 建议 | 理由 / 代价 |
|---|---|---|
| D1 | 独立 Rust 实现，不逐行翻译旧代码 | 明确模块边界；重新建立协议正确性与测试成本 |
| D2 | Tokio 单 worker + 协议库窄封装起步 | 避免自写事件循环；需证明内存与目标支持 |
| D3 | 复用系统 dnsmasq，代理走 Xray tunnel | 保持集成边界，不另写 DHCP/SOCKS |
| D4 | JSON 完整快照 + Unix socket ACK | 便于 ucode 渲染与明确失败；控制协议需版本化 |
| D5 | 第一版重载全部清缓存、取消旧请求 | 一致性优先；会产生短暂失败与缓存变冷 |
| D6 | 必需 nft 写入成功后才返回 DNS | 减少错误路由；集合故障会影响相应 DNS 可用性 |
| D7 | 原生 DoT 单独资格，不默认降成明文 | 不隐含功能倒退；TLS/根证书引入额外成本 |
| D8 | 不承诺兼容全部 CLI、ipset、旧缓存 DB | 缩小长期维护面 |

## 3. 审定前必须回答

1. **许可**：独立实现代码采用 MIT/Apache-2.0、GPL-3.0-or-later，还是主动选择 AGPL？文档如何授权？直接改编上游代码的路线与独立实现路线不可混为一谈。
2. **首版设备范围**：x86_64/aarch64、至少 128 MiB 可支配内存的验证起点是否合适？需要多早覆盖 ARM32/MIPS？这些会影响依赖选择。
3. **DoT / IPv6**：首个可替换版本必须完整覆盖哪些已有配置？未支持时严格阻止迁移，还是扩大首版范围？
4. **未知域名选择**：多个 A 全国内才选国内、非 A 只查 trust、不做判决缓存，是否接受这些有意变化？哪些必须先与固定上游实测后决定？
5. **set ACK 失败**：接受相关查询 SERVFAIL 的默认策略吗？这是可用性与错误出口风险的明确权衡。
6. **nft 后端**：内核分类查询能否以可维护方式实现？若不可行，是否接受用户态 CIDR 副本与版本同步成本？
7. **set 屏障协议**：aether-proxy 能否在表替换时增加明确的 begin/end 维护屏障？无法合作时必须承认竞争窗口。
8. **缓存默认**：3600 秒 stale 与第一版不缓存负应答是否合适？是否希望默认禁用 stale、由集成配置显式打开？
9. **重载体验**：先用完整清缓存/取消旧查询，还是需要首版就做差异重载？建议先简单正确，不预支复杂度。
10. **工程预算**：是否接受先完成 P0–P2 风险原型，再决定全量开发？若关键门槛失败，仍保留维护型 fork/继续使用上游的退路。

## 4. 交叉审查建议格式

每条意见请包含：

- 严重级别：阻断 / 重要 / 建议。
- 对应文件与章节。
- 最小失败场景：输入、事件顺序、实际风险。
- 建议修正及其代价。
- 需要补充的实验或验收断言。

重点检查：

- 是否承诺了无法同时成立的语义（例如集合副作用“绝对原子”、DNS 全可用且必不误路由）。
- 是否把内存安全当作完整协议安全。
- 是否遗漏旧 DNS 行为或错误地把上游组优先级当作全局规则顺序。
- 是否能用确定性测试证明慢上游/取消/reload/ACK 迟到不会破坏状态。
- 模块是否为了“将来扩展”过度抽象，或把 aether-proxy 职责迁进引擎。
- 原型能否真正证伪选型，而不是先实现后为现状找理由。
- 文档是否把候选依赖/资源预算写成了验证结论。

本稿没有任务卡或工期承诺。通过交叉审查后，先记录决策，再拆 P0/P1 的小任务；不要直接并行展开所有模块。
