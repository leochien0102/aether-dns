## B1：接受范围拆分，不接受“形态 B 必然只剩组转发”

**采纳**：02 §2 分 A/B 栏；通用核心不依赖 nft；形态未定时只做 P1 协议/传输/调度骨架，兼容层需另行批准。

**需要更正的推导**：

1. 原 `13-routing.md` 第 43–44 条仍判断 udirect4/uproxy4，§渲染同时又说这些集合不引用且语义不变；这是草案矛盾，不是它们已被明确废弃。
2. 即便 Xray 接管业务流量路由，DNS 的国内 CDN 选择、未知域名双组选择与缓存行为仍是独立需求。只有明确更改 DNS 解析策略，分类/双组选择才会变成可移除项。
3. 已做的 dnsmasq 17 项断言覆盖基础组转发，不覆盖未知域名双组选择、旧集合契约等完整替换语义，不能证明它已覆盖全部未来 DNS 行为。

**剩余决定**：是否要求 aether-dns 可独立替换现行形态 A？这与远端分流不急并不冲突。若要求，兼容层是有价值的支持范围，而非必然作废的投入。

## B2：不接受“内核不支持”的事实结论，保留后端选型

复核了报告指定的 **Linux v6.18.52** [nft_set_rbtree.c](https://github.com/gregkh/linux/blob/v6.18.52/net/netfilter/nft_set_rbtree.c)：

- `nft_rbtree_get()` 把查询交给 `bsearch(..., nft_array_get_cmp)`。
- 比较器计算 `a = key - from` 与 `b = key - to`（源码实际用 memcmp），无 END flag 时 `a >= 0 && b < 0` 即区间内命中。
- 因而 `ops->get()` 与 `ops->lookup()` 是两个入口，不等于前者必然仅精确 key；必须看具体后端实现。
- 固定 ChinaDNS-NG 的 [ipset.c](https://github.com/zfl9/chinadns-ng/blob/23af4b1b924fd06c67997fe35840ec7f8064ca31/src/ipset.c) 也通过 GETSETELEM 做 nft 成员测试，并非必须 dump 全表。

上述只构成源码反证，不宣称所有内核/set 后端都相同。实际目标需要隔离实验：建 interval 集合含 `192.0.2.0/24`，分别查起点、内部 `192.0.2.123`、末地址和外部地址，记录内核/nft 版本、实际后端与请求/应答。

**同源 CIDR 快照仍是合理候选**，可简化查询路径和权限，但不是因为内核绝无能力而唯一可选。相同 hash 只能保证输入同源，不能让两个进程应用时刻原子一致；两侧切换仍需停查/屏障、代次确认及失败恢复，不能声称 skew 自动归零。

因此修改为 classifier 与 nft_writer 分离，P0 二选一，不把 P2 后端验证删除为“必然失败”。

| I3 表不存在拖累 DNS | 接受风险，不接受无条件 ENOENT 放行 | 02 §4.2 明确 required 模式；仅外层确认拦截摘除且策略允许时显式关闭要求；补“仅缺一个集合但拦截仍在”反例 |
| I4 reload 集成未冻结 | 接受 | 02 §6.1 给出 restart-v1 的 argv、hash、readiness、确切回滚动作；hot-v2 另批，未知结果先核对状态 |
| I5 负缓存/判决缓存叠加成本 | 接受 | 01 §5、03 §4 增加上游请求/隧道字节/NXDOMAIN 比例测量，P3 评估 RFC 2308 负缓存开关 |

I3 的边界：报告已正确指出 fail_open 仅 flush prerouting 而保留集合；所以 ENOENT 不是 fail_open 的可靠信号。突然删表也不保证所有用户都允许泄漏，不能由引擎猜测全局故障策略。required 下失败范围只覆盖需要写入的查询，不是无条件“全部 DNS 全挂”。
